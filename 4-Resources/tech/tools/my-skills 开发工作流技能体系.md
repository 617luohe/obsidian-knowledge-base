# my-skills v2 开发工作流技能体系

> 一句话定义：一套覆盖从项目启动到收尾全生命周期的 Claude Code 技能链，通过 **24 个结构化技能**（三层架构）串联需求分析、设计、编码、审查、调试、版本管理和知识整理。

## 一、架构全景

### 三层架构

```
┌─────────────────────────────────────────────────────┐
│  ① 路由器层（1 个）                                      │

├─────────────────────────────────────────────────────┤

│     阶段 0-6 开发流程 + 扩展能力 + 独立方法论                 │
│     委托核心逻辑到 vocabulary，自身保持 30-80 行精简编排        │
```

## 二、命名规范

| 类型 | 命名格式 | 示例 | 说明 |
|---|---|---|---|
| **阶段技能** | `N-中文名称` | `0-启动`、`1-规划`、`2-开发` | N 为阶段编号 0-6 |
| **扩展能力** | `0--英文名称` | `0--claude`、`0--laoyoutiao` | 双连字符区分单连字符阶段 |
| **路由器** | `0-询问luohe` | `0-询问luohe` | 唯一入口 |
| **vocabulary 层** | `vocabulary/英文名称` | `vocabulary/grilling` | 可复用核心，不直接调用 |
| **独立方法论** | 英文或中文名称 | `multi-worker` | 不属于主流程的独立技能 |

**命名约束**：
- 阶段技能必须以 `N-` 开头（N=0-6），后接中文名称
- 扩展能力必须以 `0--` 开头（双连字符），后接英文名称
- vocabulary 层必须位于 `vocabulary/` 子目录下

## 三、技能详述

### 3.1 路由器（入口）

#### `0-询问luohe` — 技能路由器

**一句话**：不知道用哪个技能？直接说需求，自动匹配。

**职责**：理解用户自然语言需求 → 对照路由表匹配技能 → 展示计划 → 执行。替代旧版 `use-skills`。

**调用分类**：仅用户调用。

---

### 3.2 阶段 0：预备（4 个技能）

#### `0-启动` — 项目脚手架

**一句话**：新 Python 项目最小初始化（结构 + git + uv）。

**触发**：`/0-启动` | 调用：仅用户。

#### `0--claude` — CLAUDE.md 初始化器

**一句话**：一键生成/注入 CLAUDE.md 规则块。

**触发**：`/0--claude` | 调用：允许模型。

**生成内容**：称呼规则 + Caveman 简洁规则 + Karpathy 编码准则 + 工作流路由 + 项目信息占位符。非破坏式注入，已有内容不动。

#### `0--neat-freak` — 知识库洁癖审查

**一句话**：OCD 级别审查，校准文档↔代码一致性、尺寸体检、记忆毕业、消除矛盾。

**触发**：`/0--neat-freak` 或"同步一下、整理文档、梳理一下" | 调用：仅用户。

**与 `6-最后整理` 的分工**：`6` 沉淀本次会话产出（加法），neat-freak 校准全局知识库（减法/校准）。

#### `0--tokenless` — 超压缩沟通模式

**一句话**：极度精简回复，删除冠词/填充语/客套。

**触发**：`/0--tokenless` 或 "caveman mode" | 调用：允许模型。持续生效直到 `stop caveman`。

---

### 3.3 阶段 1-2：设计（2 个技能）

#### `1-规划` — 方案设计与任务拆解

**一句话**：写代码前系统性理清需求、设计接口、输出 PRD、拆解任务。

**触发**：`/1-规划` | 调用：仅用户 | 委托：`vocabulary/grilling` + `vocabulary/domain-modeling`

**6 个子阶段**：
1. **方案 grilling** — 先查事实（代码/文档），再批量询问同层决策；逐步意图触发一次一问
2. **领域术语** — 只更新 CONTEXT.md，标记模糊词汇和歧义
3. **决策记录** — 对难逆转、有真实取舍的决策创建 ADR
4. **接口设计** — 并行生成多种方案对比
5. **输出 PRD** — 结构化需求文档
6. **拆解任务** — 垂直切片，标注 AFK/HITL

**v2 新增**：原型验证门禁 — 状态机/算法/UI 不确定时，在 `docs/prototypes/` 建立 throwaway prototype。

#### `2-开发` — TDD 编码实现

**一句话**：pytest 驱动，红-绿-重构循环，四条编程准则贯穿。

**触发**：`/2-开发` | 调用：允许模型 | 委托：`vocabulary/tdd`

**流程**：规划（确认接口+列出测试行为） → 示踪弹 → RED→GREEN 递增循环 → 重构 → 自检 → 交接给 `/3-检查`。

**测试策略**：按行为风险决定自动化回归测试，不是按任务规模。不可测试时必须说明 seam 缺失和风险。

---

### 3.4 阶段 3-4：质量（2 个技能）

#### `3-检查` — 代码审查与验收

**一句话**：由输入契约自动路由 — Review / 建单 / 架构评估 / 转调试。

**触发**：`/3-检查` | 调用：允许模型 | 委托：`vocabulary/code-review`

**四种模式（自动路由）**：
| 输入来源 | 路由 |
|----------|------|
| 来自 `/2-开发` 或 `multi-worker`（带审查基点+需求来源+diff） | **强制 Review** |
| 有现象且明确要记录/建 issue | **只建单** |
| 明确输入"架构评估" | **架构评估** → 产出 `docs/analysis/` + `docs/plans/` |
| 要求找根因或立即修复 | **转 `/4-调试`** |

**Review 输出**：必须输出 `PASS` / `PASS WITH WARNINGS` / `FAIL`。

#### `4-调试` — 结构化调试

**一句话**：六阶段系统化排查难复现的 bug 和性能问题。

**触发**：`/4-调试` | 调用：允许模型 | 委托：`vocabulary/diagnosing-bugs`

**六阶段**：构建可比较观测信号 → 复现与最小化 → 假设（3-5 条）→ 工具验证 → 修复 + 回归测试 → 清理。

**核心原则**：不建立可比较观测信号不假设；稳定复现是修复验收条件而非进入调查的前置。

---

### 3.5 阶段 5-6：交付（2 个技能）

#### `5-版本管理` — Git 版本控制

**一句话**：git 全流程操作（init / save / log / diff / rollback / branch / remote / push）。

**触发**：`/5-版本管理` | 调用：仅用户。

**原则**：`/2-开发` 和 `/3-检查` 默认不改动提交；审查通过后由用户显式调用本技能才保存版本。

#### `6-最后整理` — 会话收尾与沉淀

**一句话**：本次会话的沉淀 + 物理整理，动作偏加法。

**触发**：`/6-最后整理` | 调用：仅用户。

**四步骤**：修改总结 → 经验沉淀（agent memory）→ 项目结构整理 → 交接 + 安全护栏。

**与 `0--neat-freak` 的分工**：`6` 管本次会话产出（加法），`0--neat-freak` 管全局知识库校准（减法/校准）。

---

### 3.6 独立方法论（3 个技能）

#### `0--dialectic` — 辩证矛盾分析法

**一句话**：六步法分析复杂问题、制定战略决策。

**触发**：`/0--dialectic` | 调用：仅用户。

**六步**：调查研究 → 定性 → 矛盾分析 → 阶段划分 → 策略制定 → 持续复盘。

#### `0--laoyoutiao` — 老油条：交付节奏管理

**一句话**：面向甲方 Python 项目，逐步展示优化成果、控制交付节奏。

**触发**：`/0--laoyoutiao` | 调用：允许模型。

**核心机制**：兼容优先（复用现有框架）→ 分支开关 → 叙事线分类 → 交付路线图 → 甲方可读交付说明。

**五种路径**：初始化 → 交付建议 → 精确切换 → 状态查看 → 交付说明生成。

#### `multi-worker` — 并行开发编排器

**一句话**：已有完整设计文档 + 可拆为 2-5 个互不冲突的子任务时，调用宿主 worker Agent 并行实现。

**触发**：`/multi-worker <已确认的 tasks.md 路径>` | 调用：仅用户（实验性）。

**前置门禁**：设计文档必须包含目标/模块/接口/验收标准 → Agent 配置核对 → 工作区必须干净 → 每个 worker 独立分支 + worktree。

## 四、vocabulary 核心层

> 详见 [[my-skills vocabulary 核心层详解]]

| 技能 | 职责 | 被谁调用 |
|------|------|---------|
| **grilling** | 询问循环（批量/逐步模式、事实/决策分流、推荐答案） | `1-规划` |
| **domain-modeling** | 领域建模（CONTEXT.md 维护、术语冲突标记、ADR 创建） | `1-规划` |
| **tdd** | TDD 循环（红-绿-重构、按行为风险测试、编码准则） | `2-开发`、`multi-worker` |
| **code-review** | 代码审查（Standards + Spec 双轴、并行子代理） | `2-开发`、`3-检查`、`multi-worker` |
| **diagnosing-bugs** | Bug 诊断（六阶段、可比较观测信号、根因验证） | `4-调试` |

**优化收益**：
- 阶段技能从 150+ 行简化到 30-80 行（委托到 vocabulary）
- 核心逻辑可复用（如 `grilling` 被多个技能调用）
- 边界清晰（vocabulary = 可复用层，阶段技能 = 编排入口）

| 技能 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| **1-规划** | 150+ 行 | 80 行 | ↓ 47% |
| **2-开发** | 80 行 | 60 行 | ↓ 25% |
| **3-检查** | 100 行 | 50 行 | ↓ 50% |
| **4-调试** | 100 行 | 50 行 | ↓ 50% |

## 六、推荐使用路径

| 场景 | 技能组合 | 说明 |
|------|---------|------|
| **全流程新项目** | `0-启动 → 0--claude → 1-规划 → 2-开发 → 3-检查 → 5-版本管理` | 从零到提交 |
| **接手遗留代码** | `1-规划（事实调查） → 3-检查（架构评估） → 2-开发 → 3-检查` | 先理解再改进 |
| **修复 Bug** | `4-调试 → 2-开发 → 3-检查` | 结构化排查修复 |
| **快速原型验证** | `1-规划（原型验证门禁） → 2-开发` | 试错后正式实现 |

| **知识库维护** | `0--neat-freak` | 全局文档/记忆校准 |

## 七、部署

> 详见 [[my-skills 部署与治理指南]]

**一键同步**（在项目根执行）：
```powershell
.\my-skills\scripts\sync-skills.ps1       # 正式同步
.\my-skills\scripts\sync-skills.ps1 -DryRun  # 预览
```

同步只管理本仓库拥有的技能，不会清空 `.claude/skills/`、`.cursor/skills/` 或 `.codex/skills/` 根目录。每个目标根维护 `.my-skills-managed.json` 记录受管技能。

**治理验证**：
```bash
python scripts/validate_skills.py
python scripts/validate_skills.py --check-deployments
```
