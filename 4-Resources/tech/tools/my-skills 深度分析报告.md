## 二、架构设计分析

### 2.1 三层架构：v2 最大的结构创新

v1 采用的是"独立层 + 流程层"的扁平两层结构。v2 引入了 **vocabulary 核心层**，形成"路由器 → 阶段技能 → vocabulary"三层结构。

```
┌──────────────────────────────────────────┐
│  路由器层    │ 自然语言 → 技能匹配          │  1 个
├──────────────────────────────────────────┤
│  阶段技能层  │ 编排入口，委托到 vocabulary   │  13 个
├──────────────────────────────────────────┤
│  vocabulary │ 可复用核心循环               │  5 个
└──────────────────────────────────────────┘
```

**三层之间的调用关系**：

```
路由器层    0-询问luohe
               │
               ▼
阶段技能层  1-规划 ────────────→ 2-开发 ────────────→ 3-检查
               │                    │                    │
               ▼                    ▼                    ▼
vocabulary  grilling             tdd                code-review
            domain-modeling      code-review        (diagnosing-bugs)

阶段技能层  4-调试 ────────────→ multi-worker
               │                    │
               ▼                    ▼
vocabulary  diagnosing-bugs      tdd + code-review
```

**关键洞察**：vocabulary 层不是"底层库"，而是**可替换的执行引擎**。每个 vocabulary 技能是独立完整的"提示程序"，阶段技能只负责编排——决定何时调用、如何组合、怎样传递结果。

### 2.2 委托模式：从"写规则"到"编排规则"

v1 的阶段技能是"全栈"的——包含完整的执行规则。v2 的阶段技能是"编排"的——只描述流程框架，具体执行委托给 vocabulary。

这是从**单体架构**到**微服务架构**的思维迁移：

| 维度 | v1（内联） | v2（委托） |
|------|----------|----------|
| 技能职责 | 包含全部规则和执行逻辑 | 只描述流程框架和编排逻辑 |
| 规则复用 | 复制粘贴，各自维护 | 提取到 vocabulary，单一事实来源 |
| 变更影响 | 改一个模式需同步多个文件 | 改 vocabulary 自动影响所有调用者 |
| 文件长度 | 80-150+ 行 | 30-80 行 |
| 可测试性 | 无法独立测试核心逻辑 | vocabulary 可独立测试和评估 |

**量化效果**：

| 技能 | v1 | v2 | 减少 |
|------|-----|-----|------|
| 1-规划 | 150+ 行 | 80 行 | ↓ 47% |
| 2-开发 | 80 行 | 60 行 | ↓ 25% |
| 3-检查 | 100 行 | 50 行 | ↓ 50% |
| 4-调试 | 100 行 | 50 行 | ↓ 50% |

### 2.3 编号精简：从 0-9 到 0-6

v1 有 10 个流程阶段（0-9），v2 精简到 7 个（0-6）。被移除的三个阶段：

| 移除的技能 | 整合到 | 理由 |
|-----------|--------|------|
| `2-分析`（代码概览） | `1-规划`（事实调查阶段）+ `3-检查`（架构评估模式） | 代码概览是规划和检查的一部分，不是独立阶段 |
| `3-原型`（原型验证） | `1-规划`（原型验证门禁） | 原型验证是规划中的决策工具，不是独立阶段 |
| `6-优化`（重构计划） | `3-检查`（架构评估模式） | 发现架构问题和制定重构计划是一体的 |

**精简的哲学**：一个阶段对应一个**不可再分的开发活动**。"先分析代码"不是独立阶段——它是规划和检查的前置动作。"先原型验证"不是独立阶段——它是规划中的决策辅助。

### 2.4 命名规范的工程化

v2 引入了严格的命名规范，区分三种前缀：

```
N-名称      → 阶段技能（单连字符）
0--name     → 阶段 0 扩展能力（双连字符）
vocabulary/ → 核心层（子目录）
```

这个规范不是装饰性的——它驱动了验证脚本的自动检查：

```bash
python scripts/validate_skills.py
# 自动检查：阶段技能是否以 N- 开头？
#         扩展能力是否以 0-- 开头？
#         vocabulary 是否在子目录？
#         非阶段技能是否误用了 N- 格式？
```

### 2.5 调用分类：user / model / vocabulary

v2 为每个技能引入了 `invocation` 分类：

| 分类 | 数量 | 含义 |
|------|------|------|
| `user` | 10 | 只能由用户显式输入调用 |
| `model` | 14 | 模型可按描述自动调用，用户也可显式调用 |
| `vocabulary` | 5 | 不被用户和模型直接调用，只被其他技能委托 |

这个分类解决了一个实际问题：某些技能（如 `multi-worker`、`1-规划`）需要用户明确意图，不应被模型"猜测"触发。另一些（如 `2-开发`、`3-检查`）则可以作为工作流中的自动步骤。

## 三、设计哲学

### 3.1 "技能即提示程序"

v2 延续并深化了 v1 的核心理念——每个 SKILL.md 不是文档，是**可执行的指令**。vocabulary 层的引入让这个理念更纯粹：vocabulary 技能是被"调用"的，就像编程语言中的函数调用。

### 3.2 "委托优于内联"

这是 v2 最鲜明的设计原则。当一段规则可能被多个技能使用时，提取为独立的 vocabulary 技能，而不是在每个调用处复制粘贴。这带来了单一事实来源、独立测试、独立版本管理等好处。

### 3.3 "编排与执行分离"

阶段技能是**编排器**（描述做什么、按什么顺序），vocabulary 技能是**执行器**（描述怎么做）。这种分离让两个层可以独立演化——改善 grilling 的交互模式不影响 1-规划 的阶段流程，调整 1-规划 的阶段顺序不需要改动 grilling。

### 3.4 "先了解，再行动"

v1 的调查先行原则在 v2 中得到了更系统的支持。`1-规划` 的阶段 1 不再是直接开始追问，而是先扫描 CONTEXT.md 和 ADR（事实调查），然后才进入 grilling（决策询问）。`4-调试` 的阶段 1 要求先建立可比较的观测信号，然后才能进入假设。

### 3.5 "自动化治理"

v2 从手工维护（手动 cp、手动检查命名规范）升级为自动化治理（sync-skills.ps1、validate_skills.py、skills-manifest.yaml）。

## 四、技能交互拓扑（v2）

### 4.1 显式引用关系

```
0-询问luohe ────────→ 所有阶段技能和独立方法论（调度关系）

1-规划 ──→ grilling（决策树追问）
       ──→ domain-modeling（术语建模 + ADR）

2-开发 ──→ tdd（红-绿-重构循环）
       ──→ code-review（自检审查）
       ──→ 3-检查（正式验收交接）

3-检查 ──→ code-review（双轴审查）
       ──→ 4-调试（修复模式时转调试）

4-调试 ──→ diagnosing-bugs（六阶段诊断）
       ──→ 2-开发（修复实现）
       ──→ 3-检查（修复后审查）

multi-worker ──→ tdd（worker 内 TDD）
             ──→ code-review（worker 内审查 + 验收）
             ──→ 3-检查（集成后验收）

6-最后整理 ──→ 0--neat-freak（发现知识腐烂时）
```

### 4.2 新增交互路径（v2）

| 路径 | 说明 |
|------|------|
| `0-询问luohe → 0--laoyoutiao` | 需要控制交付节奏时 |
| `0-询问luohe → 0--neat-freak` | 知识库维护请求 |
| `2-开发 → 3-检查` | 开发和审查默认不改动提交，审查是正式交接 |
| `3-检查（架构评估） → docs/analysis/ + docs/plans/` | 发现架构问题时产出分析报告和改造计划 |
| `6-最后整理 → 0--neat-freak` | 收尾时发现文档腐烂，转洁癖审查 |

## 五、优势总结

### 5.1 可维护性跃升

vocabulary 提取让核心逻辑的维护从"改 N 处"变成"改 1 处"。如果改善 grilling 的交互模式，所有调用它的技能自动受益。

### 5.2 三层架构的清晰边界

每一层有明确的职责和边界：路由器负责匹配、阶段技能负责编排、vocabulary 负责执行。没有跨层混淆。

### 5.3 自动化工程化

从手动维护到 manifest 驱动 + 同步脚本 + 验证脚本，v2 具备了专业软件项目的工程化水平。`CONFLICT` 检测、受管清单追踪、失败回滚——这些机制让部署不再是"祈祷式操作"。

### 5.4 跨平台一致性

通过 `hosts` 字段和统一的同步脚本，确保 Claude Code、Cursor、Codex 三个平台的技能版本一致。

### 5.5 治理可验证

命名规范、目录结构、manifest 一致性都有了自动化验证，不再是口头约定。

### 5.6 阶段精简化

从 10 个流程阶段精简到 7 个，去掉了不是独立开发活动的阶段（分析、原型、优化），降低了认知负荷。

## 六、可改进之处（v2 更新）

### 6.1 vocabulary 的回归测试

vocabulary 是"提示程序中的提示程序"，目前没有独立的回归测试。当 grilling 的交互逻辑改变时，如何验证 1-规划 的行为没有退化？

**建议**：为每个 vocabulary 技能建立 eval 用例——一组标准输入和期望输出。

### 6.2 vocabulary 的版本锁定

阶段技能目前不锁定依赖的 vocabulary 版本。如果 vocabulary 发布了 breaking change，所有依赖它的阶段技能会静默地行为改变。

**建议**：在 manifest 的 `dependencies` 中支持版本约束（如 `vocabulary/grilling: ^1.2.0`）。

### 6.3 多平台行为差异

虽然技能内容相同，但 Claude Code、Cursor、Codex 的 skill 加载和执行机制可能有差异。目前没有针对多平台的兼容性测试。

**建议**：为每个目标平台建立最小兼容性验证。

### 6.4 路由器路由表的手工维护

`0-询问luohe` 的路由表仍然是硬编码的。随着技能数量增长（从 13 到 24），维护成本上升。

**建议**：从各技能 SKILL.md 的 frontmatter/description 自动生成路由表。

### 6.5 `0--dialectic` 参考文件仍缺失

v1 分析报告指出的 6 个引用参考文件（句式武器库、回答范例等）仍然缺失。

**建议**：补全或移除引用。
